# TruHire Engineering Instructions

## Project context

- TruHire is a mobile-first platform for frontline workers built with React Native, Expo, Expo Router, and TypeScript. The primary environment is Windows with VS Code and Codex; GitHub is used for source control.
- Prioritize mobile usability, performance, accessibility, and cross-platform compatibility. Test iPhone changes through Expo Go when practical.
- Protect employee data and privacy. Do not add public employee ratings, reputation scores, rankings, or employee scoring without explicit product-owner approval and clear privacy, consent, and fairness requirements.

## Before changing code

1. Read this file and any applicable `AGENTS.md` files in directories relevant to the change.
2. Inspect the relevant implementation, `package.json`, lockfile, and Git status before editing. Preserve existing user changes.
3. Check the installed Expo SDK, React Native, and Expo Router versions; do not rely on remembered APIs. Read the matching versioned Expo documentation and use `https://docs.expo.dev/llms.txt` to find the relevant pages.
4. Expo Router routes belong under `src/app/`; `_layout.tsx` files define navigators. Keep reusable components, hooks, and utilities outside `src/app/`. Import router APIs from `expo-router`.
5. Check available scripts and installed tools before choosing commands. Do not assume a test runner or lint setup exists.

## Git workflow

- Use a small, isolated feature branch for feature work. AI agents must never merge their own feature branches into `main` without the user's explicit approval. Prefer a reviewed GitHub pull request with all required checks passing before merge.
- Keep changes focused. Before finishing, inspect the complete diff and Git status for accidental changes, generated files, secrets, lockfile updates, and unrelated edits.
- Do not change Git configuration or line-ending settings without the user's approval.
- Report the exact files changed and summarize behavior changes. If a normal diff cannot show changes, state that limitation.

## Dependencies, Expo, and native projects

- Do not install, remove, or upgrade dependencies without the user's explicit approval. Use the package manager indicated by the lockfile. Install Expo packages with `npx expo install <package>` after approval so versions match the project's SDK.
- Expo Go includes only its bundled native modules. A dependency that adds native code generally requires a development build; check the matching Expo documentation before choosing a workflow.
- If `ios/` or `android/` is absent, treat native projects as generated by Expo Continuous Native Generation. Configure native behavior through app config and config plugins; do not create generated native directories by hand. If those directories exist, inspect their status and relevant instructions before changing them.
- Check whether commands may install dependencies or modify project files. Do not run destructive reset, clean, migration, or overwrite commands without explicit approval.

## Validation and reporting

- Run applicable checks available in the project, such as configured lint, typecheck, or relevant tests. Run tests only when a test runner and relevant tests exist or are added as approved work.
- Report every check as passed, failed, or not run, with useful failure details. Never claim a check passed unless it completed successfully.
- Typechecking alone does not establish that a runtime issue is fixed. State whether the app was launched or the affected flow exercised.

## Secrets and sensitive data

- Never reveal, copy into output, or commit secrets, credentials, signing keys, tokens, or private employee data. Do not print secret values while inspecting configuration; if a secret appears in output or a diff, do not repeat it and flag the exposure safely.
- Never commit `.env` files or other secret-bearing files. Keep local environment files out of Git with an appropriately maintained `.gitignore`.
- Treat employment history, skills, achievements, identity, and contact details as sensitive personal data. Collect, display, store, or share only what an approved feature requires, and preserve consent and privacy expectations.

## Approval for high-impact operations

- Obtain the user's explicit approval before pushing to shared branches; changing GitHub settings or secrets; installing or upgrading dependencies; applying sensitive database migrations; changing security or access policies; deploying to production; or performing destructive, costly, difficult-to-reverse, or other high-impact operations.
- Before requesting approval, explain the proposed change, affected systems, and material risks. Do not perform approved high-impact work beyond its approved scope.
